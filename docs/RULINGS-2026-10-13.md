## 1 — Format definitions are base doctrine

**Finding.** Law 2 covered three kinds of payload (narrative spec, JSON Schema,
layout grammar) and law 11 named a short list of "boring" encodings. Neither
said what happens to a JPEG a photographer imported, a font a document embeds
or a camera raw file. Measured in the corpus: eight applications each invented
an answer — an extension node, a `meta` key, `encoding: "other"`. Both
reference manifest schemas were closed against an unknown top-level key, so a
`3d-entity/1` or `image/1` package could not carry a `formats` map at all, and
the one library that had built the mechanism carried the map on a node, as
`meta.format_definitions`.

**Proposed rule (SPEC §3.18).** A payload in any encoding is a legitimate
`core.*` payload when, and only when, the package carries a definition of that
encoding from which a codec can be built. The original bytes travel verbatim.

* **(a) Where a definition lives.** One markdown document per format at
  `spec/formats/<format id>.md`, a file of a `core.spec` node. It begins with a
  machine-readable header: a fenced block with info string `werk-format`
  holding one JSON object (`format_id`, `format_version`, `sniff`, `defines`,
  `coverage`, `coverage_note`, `requires`, `reference_tools`, `test_vectors`,
  `vector_files`, and others; the table is in §3.18).
* **(b) The manifest's `formats` map** — format id → path — parallel to
  `schemas` and `layouts`. Both reference manifest schemas and the base schema
  admit it.
* **(c) How a node declares its payload's format.** In `meta`:
  `payload_format` (the payload file), `file_formats` (role → id, for other
  files of the node), `contained_formats` (ids of the streams inside a
  container format). A declaration beats a sniff.
* **(d) Test vectors are what make it a definition.** At least one; the input
  is printed in a `hex <vector id>` block or carried as a declared file under
  `spec/formats/vectors/`; `output_form` states the canonical decoded form and
  `output_sha256` its hash.
* **(e) Reference implementations are a convenience** and are `core.tool`
  nodes: source only, never executed automatically (§7.1 unchanged). Where a
  reference and its document disagree, the document is the norm.
* **(f) Partial coverage is legal and must be exact** (`coverage: "partial"`
  with a mandatory `coverage_note`).
* **(g) `spec_sha256` covers the definitions and their vector files**, because
  they are files of a `core.spec` node. No change to the construction.
* **(h) What a reader does without a codec**, and reports: four checks, four
  codes (`format-definition-invalid`, `format-undeclared`, `format-mismatch`),
  all `warn`; it states how many definitions it read and how many vector
  inputs it re-hashed. It never decodes a payload to validate a definition and
  never runs a reference implementation.

**Reconciliation with CRAFT-BASE §6** (`craft-libs-core/crates/werk/assets/
craft/CRAFT-BASE.md`). The mechanism is the same one. Three differences, each
decided in the reference's text and each for the ArtCraft side to follow
(listed in the change list of the final report):

1. The map's home is the manifest's `formats`. `meta.format_definitions` on a
   node is the legacy location; a reader looks in `formats` first and there
   second, so packages already written keep resolving.
2. A format id names one document **within a package**. Across packages the
   document a package carries is the authority for that package (the rule §2.2
   gives a schema). CRAFT-BASE words identity as global ("one id, one
   document"); the reference cannot check that and does not claim it.
3. `sniff` must be a non-empty list; a format with nothing to recognise says
   `{"rule": "none", …}`.

**The reference's own worked example** is `spec/formats/splat-32.md`: the
32-byte `.splat` record, two vectors, checked by `tools/format_def.py` (a
second implementation of the header rules, in Python, sharing no code with
`core/src/formats.rs`). `fixtures/gsplat-v1.werk` declares its recipe's input
medium with `file_formats: {"input-media": "splat-32"}`.

**Part c — `core.revisions` (SPEC §3.19).** Finding: law 6 keeps versions per
node, so "the document as it was at the second Save" is not derivable from
`versions[]`. Three independently written writers each built a log for it and
each put it where a core reader does not look (`x.craft.revisions` under the
reference profiles, an `x.spark.scene` log, an `x.*` photo node). Proposed: a
core type `core.revisions`, one node per package, one version per Save, the
record shape `craft-werk` already writes, adopted so its packages validate
(`spec/schemas/core.revisions.schema.json`; both manifest schemas admit the
type). Stated cost: a record is linear in the node count.

**Implemented less than proposed.** The reference core validates a
`core.revisions` payload against the schema the package ships; it does **not**
check that each record's `nodes` values exist in `versions[]`, nor that
`active` agrees with the active record. No reference writer emits the node.

## 2 — Any profile, not two

**Finding.** The reference core on `master` answered every package of a
profile other than `3d-entity/1` and `image/1` with `[error]
unsupported-convention: this build carries no manifest schema for profile …`
and exit status 1: **32 of 32** third-profile packages in the corpus, although
every hash and every signature in them verified. Seven packages of the two
reference profiles verified; one is damaged on purpose. The Rust and C loaders
on `master` additionally refused every Spark package (`3d-entity/1`) because
of two conventions added after their lists were typed (`sh_coeff_order`,
`sh_degree`), and both carried a list of known `core.*` types that had fallen
five types behind the manifest schema.

**Proposed rule (SPEC §2.2).**

* A profile is defined by documents that travel in the package:
  `manifest_schema` (mandatory outside the two reference profiles),
  `profile_spec`, `schemas`, `layouts`, `formats`, `conventions_map`.
* A reader holds one schema of its own, the **base schema**
  (`spec/schemas/manifest.base.schema.json`), and always applies it. A profile
  schema refines it and cannot loosen it.
* Six **base conventions** are checked against the reader in every profile:
  `endianness: "le"`, `alignment_bytes: 16`, `text_encoding: "utf-8"`,
  `id_case: "kebab-case"`, `hash_algorithm: "sha256"`,
  `signature_algorithm: "ed25519"`.
* An unknown profile is validated against the package's own schema, reported
  with exactly one `unsupported-profile` (`warn`), and its node types go down
  the skip path: listed, hash-verified, extractable, reported, never an error.
* A built-in profile whose package carries another revision of the schema is
  validated against the package's copy (`manifest-schema-revision`, `info`).
* `spec_sha256` is recomputed; a wrong one is `spec-sha256-mismatch`.

**The trust statement (SPEC §10.3)** says what validating a package against a
schema taken from that package establishes (internal coherence, the base
shape, the hashes) and what it does not (that the schema is the profile
author's, anything about meaning, that the reader supports the package), and
binds the reader: schemas are untrusted input (recursion bound 200, pattern
subject limit, unknown keywords reported once, no `$ref` leaves the document),
and a package's schema may not widen the base shape.

**Report codes** are now a closed table in SPEC §10, and the exit statuses of
the four readers agree (entry 9).

**Gate.** `tests/run_gate_artcraft.py`: every sample exits 0 in the reference
core with exactly the recorded census; the damaged one exits 1 with exactly
the recorded dead node; the three loaders agree on the verdict. The corpus is
not in this repository; `tests/artcraft-corpus.json` pins each sample by
SHA-256. An unpinned or changed sample is still verified and its line says
UNPINNED.

## 3 — Writing a minimal valid package is normative

**Finding.** The specification said what a valid package is and never how to
write one. Every writer outside this repository reverse-engineered the order
of operations from a fixture, and the two constructions they got wrong were
the two that are hashes over an ordering convention (`input_hash`,
`spec_sha256`).

**Proposed.** `spec/WRITING-3D-ENTITY.md` (SPEC §14 points at it) and
`spec/WRITING-IMAGE.md` (`PROFILE-IMAGE.md` §10) are normative. Each has an
executable half in `spec/examples/` — `write_minimal_3d_entity.py`,
`write_minimal_image.py` — using the Python standard library only, taking the
specification and loaders from any werk package it is handed and authoring
the rest. Each document quotes hashes the script prints.

**Gate.** `tests/run_gate_writing.py`: each script runs from a pinned fixture
alone; its output is read by all four readers in zip and directory form with
exit 0 and no error; two runs are byte-identical; written again from its own
output the script produces the same bytes; every hash a document quotes is
printed by the script and is the hash of a carried file or a manifest value.

## 4 — Envelopes are recognised by their frame

**Finding.** A reader recognised an envelope only if its magic was in that
reader's own copy of a table. There were four copies. The corpus carries 365
envelopes outside `core.spec` in its 40 packages, nearly all under profile or
extension kinds; a magic absent from a table was not parsed and not reported.
Every one of the 365, and of the 11 in this repository's fixtures, already has
`kind` equal to its node's type and a grammar named in `layouts`. The paper already records the same failure once (§3.1).

**Proposed rule (SPEC §3.1; `ENVELOPE.layout.txt` §2).** A file is an envelope
when its first four bytes are `W`, `K` and two characters each `A`–`Z` or
`0`–`9`, and its node does not declare it to be in another format. Its grammar
is `MANIFEST.json → layouts[header.kind]`. Outside `core.spec` the header's
`kind` equals the node's type. The seven reserved magics each bind one kind
and are a consistency check, not a recogniser. `WKX0`..`WKX9` bind no kind. A
reader states how many envelopes it validated; a well-formed envelope whose
kind has no grammar in `layouts` is `envelope-undeclared` (`warn`).

**Gate.** `tests/run_gate_magic.py`: the seven magic/kind pairs are identical
in the normative text and in the source of all four readers; on a real
package, an unknown magic is validated (core: one more envelope counted, and
`envelope-undeclared`), a broken frame under an unknown magic is
`envelope-invalid` in all four, a reserved magic over another kind is
`envelope-invalid` in all four, and four bytes that are not a magic draw no
envelope report. Writing this gate found that the Rust and C loaders killed
such a node on `--verify` without printing why; both now print
`envelope-invalid`.

## 5 — Scene state of a 3D entity

**Finding.** Spark's `3d-entity/1` scenes hold three things with no place in
the core — whether a part is shown and how (visible, opacity, tint), the
application's non-destructive edit layers, and parts scaled by a negative
number — and put all three in `x.spark.scene`. A reader that skips extensions
draws a hidden part, loses a tint, shows the unedited splat, and gets the
absolute value of a mirrored part, without a report.

**Proposed (SPEC §3.20).**

1. `parts[].transform.scale` components may be negative (a reflection) and
   are never zero. A consumer that does not implement reflections reports
   `part-reflection-unsupported`.
2. `core.scene`: at most one node, named by `primary.scene`; per part its
   transform, `visible`, optional `opacity` and `tint_linear_rgb`
   (`spec/schemas/core.scene.schema.json`). For the active version each
   transform equals `parts[]`; on disagreement `parts[]` wins for placement.
   A consumer that does not implement display state reports
   `scene-display-unsupported`.
3. `meta.modified_by` (base doctrine, every profile): a core node whose
   payload is shown differently because of state in other nodes lists those
   node ids; a reader that skips or loses one reports
   `modified-by-skipped-node`. Edit layers themselves stay `x.*`.

**Implemented less than proposed.** The schemas admit all three and the core
emits `modified-by-skipped-node`. `part-reflection-unsupported` and
`scene-display-unsupported` are in the code table and are emitted by nothing
in this repository: no consumer here draws. The Blender and Unreal adapters
do not read `core.scene`, and what they do with a negative scale was not
measured.

## 6 — The `@N` marker goes on the superseded file

**Finding.** SPEC §5 named the marker and did not say which file gets it.
`craft-werk` and the reference fixtures put it on the superseded file; Spark's
exporter and lightcraft's `image/1` writer put it on the new one. Both resolve
through `versions[]`, so no reader failed, and a document saved twice looked
different on disk depending on who saved it.

**Proposed rule (SPEC §5).** When a Save changes a file's bytes, the new bytes
take the logical path and the superseded bytes move to `stem@N.ext`, `N` being
the `v` of the version that introduced them; the marker sits before the last
extension, on the file name, never on a directory. Earlier versions' `files[]`
entries are updated to the moved path; their `sha256` and `size` never change.
Reason: the plain path then always names the current bytes, which
`container.entry_order`, `container.preview_tier` and §12's recovery rely on.

**No package becomes non-conformant and no reader changes.** Writers that must
change: Spark's exporter and lightcraft's `image/1` writer. The reference
writers already conform.

## 7 — A package carried as a payload of another

**Finding.** One manifest lists every version of every node and is rewritten
whole on every Save. Measured outside this repository: a library of 50,000
photographs is 150,000 nodes and a 183 MB manifest. The proposal made there is
to make the library fifty nodes, each a package of a thousand photographs, and
to let an inner package omit files the enclosing package already holds.

**§13.1 — PROPOSED as a statement of what the laws already say.** A node's
payload may be a complete werk package in its single-file form:
`meta.payload_format: "werk"`, and `meta.package: {profile, entity_uuid,
manifest_sha256}` so the outer manifest can be browsed. The inner package is
hermetic on its own, an island of the outer one, and custody composes.

**§13.2 — NOT a rule. A law-1 / law-2 question for Gregor.** The deduplicated
form (an inner package omitting `spec/` and `loaders/` and resolving them from
the enclosing package by hash) is stated with both readings. *For:* the werk
is the outermost file, every question is answered inside it by content hash,
and the manifesto's Companion section licenses that arrangement for a store.
*Against:* law 1's "every materialized werk remains complete … Never the
reverse" — a deduplicated inner package cut out byte for byte by a tool that
does not know the rule is a `.werk` that declares files it does not hold.

**Reference position until ruled:** the complete form is the only form a
reference writer emits and the only form a reference reader resolves; a
deduplicated inner package's omitted files are `file-missing`. Nothing about
nesting is implemented in the reference core or loaders: a nested package is
one verified file to them. A ruling for the deduplicated form must also settle
whether the rule lives in the specification, whether the form is recognisable
(its own extension or `container.form` value), and what may be inherited.

`craft-werk` writes `meta.capsule` where §13.1 says `meta.package`; one of the
two names has to change (change list, final report).

## 8 — Four inconsistencies inside the reference

Each was found by somebody writing a werk writer from the specification
alone. Each is fixed with a test.

**F-AC-1 — the example manifest failed the schema it illustrates.**
`spec/examples/MANIFEST.example.json` lacked `spec_sha256`, mandatory since
S-29. Fixed in `spec/examples/make-examples.py`; the example, its signature
and its signed-message transcript are regenerated. Test:
`the_example_manifest_validates_against_the_schema_it_illustrates`
(`core/tests/profiles.rs`), and `run_gate_reference.py` checks the worked
signature covers the worked manifest.

**F-AC-2 — the Python `canon()` escaped non-ASCII.** `pipeline/common.py` and
`tests/run_gate_3b.py` used `json.dumps` with its default `ensure_ascii=True`;
the Rust core writes non-ASCII as UTF-8, as MINI-SPECS §3 rule 3 says. No
fixture's `input_params` held a character outside ASCII, so nothing caught it.
Fixed; MINI-SPECS §3 carries a vector (52 bytes, sha256 `13a29066…`). Tests:
`canonical_json_writes_non_ascii_as_itself`, and the gate recomputes the
vector with the Python function.

**F-AC-4 — the loader capability list existed in nine places and they
disagreed.** `werk_read.py` stated six capabilities; every writer declared
four for it; the schema enum admitted neither of the two extra names
(`summarize-points`, `summarize-gsplat`), so a writer that copied the loader's
own list produced a manifest its schema rejected. Fixed: each loader states
its list in one `WERK-LOADER-CAPABILITIES:` line; the eight writers read it
from the bytes they embed (`tools/loader_caps.py`; inline in `werkc` and in
the Blender exporter); both schema enums admit the two names. Test:
`run_gate_reference.py` — line ⊆ enum, Python constant = line, and every
`core.loader` node version in every pinned fixture declares exactly its
embedded loader's list.

**F-AC-6 — three spec files were CRLF in the working tree the fixtures were
built from.** `.gitattributes` makes every text file LF, in the index and the
working tree. `<repo>` holds three files checked out before that rule
(`spec/schemas/signature.schema.json`, `spec/skeleton/canonical-humanoid-v1.json`,
`spec/skeleton/core.hands.v1.json`): `git ls-files --eol` shows `i/lf w/crlf`,
and git reports them clean. A builder run from that tree embeds the CRLF
bytes. Ruling R1 of 2026-09-09 ruled the LF hash canonical and left the
shipped fixtures on the historical CRLF snapshot; the consequence, measured on
a fresh LF checkout of `master`: `run_gate_9.py` 14 PASS 1 FAIL and
`run_gate_12.py` 17 PASS 1 FAIL, both in the "rebuild is byte-identical"
clause. Fixed on this branch: every fixture is rebuilt from an LF tree (the
specification changed, so a rebuild was due regardless), every builder refuses
a spec or loader text file containing a carriage return
(`tools/spec_sha256.py` `translated_text`; `werkc build-fixture` has the same
guard), `.gitattributes` marks `*.wkem`, `*.wkgs`, `*.wkpc` and `*.zip`
binary, and the gate checks the tree, checks that the guard refuses, and
checks that all 1,014 spec and loader files embedded in the 16 pinned fixtures
are byte-identical to the repository's. **`<repo>` itself was not touched**;
those three files there still need a re-checkout (delete, then
`git checkout -- <path>`).

**Two further findings recorded here.**

* **F-AC-5 — the CC0 fixtures were pinned nowhere**, and
  `run_gate_cc0_image.py`'s determinism clause ran the builder with its
  default output directory, which is `fixtures/`: every run of the gate
  overwrote the two shipped fixtures. Fixed: eight CC0 fixtures and the
  deflated one are in `fixtures/fixtures.json`; the three CC0 gates pin before
  measuring; the determinism clause builds into the gate's scratch directory
  and compares with the shipped bytes.
* **F-AC-3 — canonical number spelling. OPEN, not fixed.** MINI-SPECS §3
  rule 4 fixes the digits of a non-integer and not their spelling: `1e-05` is
  `1e-05` in Python and `0.00001` in Rust and JavaScript; `1.0` is `1` in
  JavaScript; `1e16` is `10000000000000000` in JavaScript. An `input_hash`
  over such a parameter is recomputed differently in different languages,
  including by this repository's own two. MINI-SPECS §3 now says so and gives
  writers the safe subset; a rule is still owed.

## 9 — Deflate is read; zip64 is refused, uniformly, by name

**Finding.** SPEC §1 said method 8 "remains legal and a reader SHOULD support
it"; no reader in this repository did and no fixture was deflated. The core on
`master` reported one deflated entry as `file-missing` and a fully deflated
package as `bad-manifest: MANIFEST.json is not in …`. A real zip64 file made
all four readers exit 1 with four different messages, one of them a Python
traceback. MINI-SPECS §5.4 said zip64 was permitted and that a full reader
SHOULD support it. Exit statuses disagreed: the core and two loaders returned
1 for an unreadable container, and the Rust loader returned 3 for `--strict`.

**Proposed.**

* **No zip64, ever.** A single-file package is a 32-bit zip: below 4 GiB, at
  most 65,534 entries. A package past that is carried in directory form, which
  is the same format and has no ceiling. A reader recognises zip64 from the
  file's tail before reading anything else and refuses the container:
  `zip64-unsupported`, exit status 2 (MINI-SPECS §5.5). A zip64 extra field in
  local headers only, with ordinary values in the central directory, is not
  zip64 and is read.
* **Deflate is read** by all four reference readers. MINI-SPECS §7.1 defines
  the bitstream with three vectors, so a PNG's pixels are also decodable from
  the specification alone. Store remains the writer default and every other
  fixture is store-mode. A stream that does not decode, or inflates to the
  wrong size or CRC, is damage to that entry: `zip-entry-invalid`.
* **Any other method, or an encrypted entry**, kills the owning node:
  `zip-entry-unsupported`.
* **Exit status** for all four readers: 0 no error entry; 1 at least one
  error entry (a bootstrap loader: with `--strict`); 2 container-scoped
  refusal.

**Fixture.** `fixtures/crate-cc0-lean-v1-deflated.werk`: the CC0 lean crate
with every entry compressed by zlib 1.3.1 at level 9, an encoder that shares
no code with any of the four inflaters. Its content is a pure function of the
repository; its container bytes are a function of the zlib version, and
`fixtures/build_deflated_fixture.py --check` compares content.

**Gate.** `tests/run_gate_container.py`: the deflated fixture against its
store-mode twin in four readers; an undecodable stream; a method-12 entry; the
local-header-only case; a real zip64 file of 70,001 entries written by the
Python standard library at run time; `--big` adds a container over 4 GiB. The
first draft of the gate expected a refusal for the local-header-only case; the
four readers were right and the gate was wrong, and MINI-SPECS §5.5 now says
why.

**Not done.** The readers in the Unreal adapter and in the CUB consumer were
not changed; whether they inflate, and whether they refuse by the same names,
was not measured.
