werk layout grammar — llama2c-checkpoint/1
==========================================

The binary layout of the file this package carries as `model/stories15M.bin`.

This grammar exists because of law 2: a werk package must carry the knowledge
needed to read its own bytes, and "it is a llama2.c checkpoint" is a name, not
a grammar. Everything below is DERIVED FROM THE RUNTIME SOURCE this package
also carries (`tools/llama2c/run.c`, functions `read_checkpoint` and
`memory_map_weights`) and then CHECKED against the actual file: the offsets in
§4 were computed from the header in §2 and they account for every one of the
file's 60 816 028 bytes with nothing left over. That check is the only reason
this document is allowed to say "MUST" anywhere.

Unlike the layouts in `spec/layouts/`, this is NOT a werk envelope. There is no
`WK**` magic, no MessagePack header and no section table. It is a foreign
format — a bare header followed by bare tensors — and werk's job here is to
describe it exactly rather than to convert it. That is the honest thing for a
container to do with a third-party artifact whose bytes must stay byte-identical
to what its author published.

1. SCALARS AND ENDIANNESS
-------------------------

  i32  signed 32-bit integer, two's complement, LITTLE-ENDIAN
  f32  IEEE 754 binary32, LITTLE-ENDIAN

The file declares no endianness of its own. Little-endian is what the runtime
assumes (it `mmap`s the bytes and casts) and it is what the manifest's
`conventions.endianness = "le"` declares for this package. A big-endian consumer
MUST byte-swap and MUST NOT read the file in place.

There is no magic number, no version field and no checksum anywhere in this
format. A reader therefore cannot tell a truncated or wrong file from a valid
one by inspection; it can only check the arithmetic of §4 against the file size.
This grammar makes that check normative:

  MUST: a conformant reader computes the total from §4 and REFUSES the file
  (node-scoped refusal, SPEC.md §10.1) when it does not equal the file size.

The manifest's own `sha256` for `model/stories15M.bin` is the stronger check and
is the one a werk reader has anyway.

2. HEADER — 28 bytes at offset 0
--------------------------------

Seven i32 in this order. These are the fields of `Config` in run.c, in
declaration order, read by one `fread(config, sizeof(Config), 1, file)`.

  off  type  name          value in model/stories15M.bin
  ---  ----  ------------  -----------------------------
    0  i32   dim                288
    4  i32   hidden_dim         768
    8  i32   n_layers             6
   12  i32   n_heads              6
   16  i32   n_kv_heads           6
   20  i32   vocab_size       32000
   24  i32   seq_len            256

Derived quantities used by §4:

  head_size = dim / n_heads                 = 48
  kv_dim    = (dim * n_kv_heads) / n_heads  = 288

THE SIGN OF `vocab_size` IS A FLAG. run.c:

    int shared_weights = config->vocab_size > 0 ? 1 : 0;
    config->vocab_size = abs(config->vocab_size);

A POSITIVE `vocab_size` means the output classifier SHARES the token embedding
table; a NEGATIVE one means a separate classifier matrix follows the RoPE
tables. In this file the value is +32000, so the weights ARE shared and there is
no trailing classifier. run.c's own comment on this is "bit yikes." It is
recorded here rather than smoothed over, because a reader that misses it reads
either 36 864 000 bytes too few or too many.

3. TENSOR ELEMENT TYPE
----------------------

Every tensor in this file is f32. There is no quantisation, no scale, no
zero-point and no per-block metadata anywhere in this format. (llama2.c has a
separate int8 checkpoint format, `version 2`, written by a different exporter
with an explicit magic and version header; this file is NOT that and a reader
must not look for one.)

Tensors are stored DENSE, ROW-MAJOR, C order, with no padding and no alignment
between them. A tensor of shape (a, b, c) occupies a*b*c*4 bytes and element
(i, j, k) is at element index ((i*b) + j)*c + k.

4. TENSOR ORDER AND OFFSETS
---------------------------

Immediately after the 28-byte header, in exactly this order. Order is
load-bearing: nothing in the file names a tensor, so a tensor is identified only
by its position in this sequence. The order is `memory_map_weights` in run.c,
line for line.

  #   name                    shape             elements     offset      bytes
  --  ----------------------  ----------------  ---------  ----------  ---------
   1  token_embedding_table   (32000, 288)       9216000          28   36864000
   2  rms_att_weight          (6, 288)              1728    36864028       6912
   3  wq                      (6, 288, 288)       497664    36870940    1990656
   4  wk                      (6, 288, 288)       497664    38861596    1990656
   5  wv                      (6, 288, 288)       497664    40852252    1990656
   6  wo                      (6, 288, 288)       497664    42842908    1990656
   7  rms_ffn_weight          (6, 288)              1728    44833564       6912
   8  w1                      (6, 768, 288)      1327104    44840476    5308416
   9  w2                      (6, 288, 768)      1327104    50148892    5308416
  10  w3                      (6, 768, 288)      1327104    55457308    5308416
  11  rms_final_weight        (288,)                 288    60765724       1152
  12  (dead) freq_cis_real    (256, 24)             6144    60766876      24576
  13  (dead) freq_cis_imag    (256, 24)             6144    60791452      24576
  --  ----------------------  ----------------  ---------  ----------  ---------
                                                     total offset 60816028

  file size of model/stories15M.bin = 60 816 028 bytes.  EXACT MATCH, no slack.

The general shapes, for a checkpoint with other hyperparameters:

   1  token_embedding_table   (vocab_size, dim)
   2  rms_att_weight          (n_layers, dim)
   3  wq                      (n_layers, dim, n_heads * head_size)
   4  wk                      (n_layers, dim, n_kv_heads * head_size)
   5  wv                      (n_layers, dim, n_kv_heads * head_size)
   6  wo                      (n_layers, n_heads * head_size, dim)
   7  rms_ffn_weight          (n_layers, dim)
   8  w1                      (n_layers, hidden_dim, dim)
   9  w2                      (n_layers, dim, hidden_dim)
  10  w3                      (n_layers, hidden_dim, dim)
  11  rms_final_weight        (dim,)
  12  (dead) freq_cis_real    (seq_len, head_size / 2)
  13  (dead) freq_cis_imag    (seq_len, head_size / 2)
  14  wcls                    (vocab_size, dim)   — ONLY when vocab_size < 0

ENTRIES 12 AND 13 ARE DEAD SPACE AND MUST STILL BE SKIPPED. run.c says so in
two comments — "skip what used to be freq_cis_real (for RoPE)" — and reads
nothing from them: RoPE frequencies are recomputed on the fly in `forward()`.
They are 49 152 bytes of a format that keeps them only so old checkpoints stay
readable. A reader that does not skip them lands 49 152 bytes early on entry 14
and, in a shared-weights file like this one, silently reads the wrong end of the
file when it looks for anything after `rms_final_weight`.

5. WHAT THIS GRAMMAR DOES NOT TELL YOU
--------------------------------------

It tells you where every number is. It does not tell you what the numbers MEAN
as an architecture: the residual stream, the RMSNorm epsilon (1e-5f), the RoPE
base (10000.0f), the SwiGLU in the FFN, the softmax and the sampler all live in
`tools/llama2c/run.c`, which this package carries as source for exactly that
reason. This document and that file are the two halves of "you can read these
bytes"; neither is sufficient alone, and the split is deliberate — a layout
grammar that also tried to be a model definition would be a paper, not a
grammar.

6. DECISIONS
------------

D-L2C-1  No conversion. The checkpoint travels byte-identical to what its
         author published (sha256 in the manifest), because a package whose
         payload does not hash to the upstream artifact cannot be checked
         against upstream at all. Re-serialising it into a werk envelope would
         have bought a section table and cost the one property that makes the
         provenance verifiable by a stranger.

D-L2C-2  The dead RoPE tables are documented as dead rather than deleted, for
         the same reason: deleting them would change the bytes.

D-L2C-3  The offsets in §4 are stated absolutely, not as a formula the reader
         must evaluate. Law 8's corollary: never make a reader derive an offset
         it could have been told. The formula is given too, in §4's second
         table, for checkpoints that are not this one.
