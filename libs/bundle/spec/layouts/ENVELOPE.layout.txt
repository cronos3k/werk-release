werk binary envelope — layout grammar v1
========================================

Applies to: every custom binary payload in a werk package (`core.field.flow`,
`core.pose.rest`, `core.anim.clip`, `core.skeleton` binary mirror,
`core.embedding`, `core.geom.points`, `core.geom.gsplat`, and any `x.*`
binary). If a file in a werk package is not
one of the boring standard
encodings (PNG / WAV / GLB / JSON / plain text — see spec/MINI-SPECS.md), it
is an envelope file and this grammar reads it.

This file is normative and self-contained: a programmer or agent with only
this file and a hex editor can write a complete reader. It assumes no
external knowledge beyond IEEE-754 and UTF-8.

--------------------------------------------------------------------------
0. Governing rules (manifesto laws 8 and 11)
--------------------------------------------------------------------------

  * ALL numeric fields in the fixed prefix and in every payload section are
    LITTLE-ENDIAN.
  * EXCEPTION, and it is the single most common implementation bug:
    MessagePack (used for the header only) encodes its integers and floats
    BIG-ENDIAN, because that is what MessagePack is. Read section 4 before
    writing a header parser.
  * Every offset and every size is DECLARED in the header. A reader never
    computes an offset from a struct definition, never infers a size from a
    count times a guessed stride, and never trusts a comment. If a declared
    offset/size pair does not fit inside the file, the node is malformed and
    the reader marks it dead and continues (law 3).
  * Payload data begins on a 16-byte boundary from the start of the file.
  * No compression inside an envelope. No varints. No bit packing in core.
    Flat POD arrays with explicit strides only.

  WORKED EXAMPLES -- READ ONE BEFORE WRITING A DECODER. This grammar is
  complete, and a complete grammar is still not a decoder; the gap between
  the two is where implementations invent numbers. Every envelope magic the
  core spec defines therefore ships a real binary and an annotated hex dump
  of it, byte by byte, through to the decoded values:

    spec/examples/restposes.example.hex.txt   WKRP, 560 B, 2 poses
    spec/examples/gsplat.example.hex.txt      WKGS, 1120 B, 3 Gaussians
    spec/examples/embedding.example.hex.txt   WKEM, 512 B, dim 8

  All three are regenerated, byte-identical, by spec/examples/make-examples.py,
  whose `mp_encode`/`mp_decode` are the executable statement of section 4 and
  whose writers are the executable statement of each layout file. Recorded as
  spec finding S-OW-3: a 30B model given section 4 and no worked example read
  it, declined to implement it, and printed fabricated floats labelled
  "demonstration" -- so the example is part of the minimum documentation set
  for any package carrying an envelope, not an optional extra.

--------------------------------------------------------------------------
1. File structure
--------------------------------------------------------------------------

  byte range              size        field
  ----------------------  ----------  ------------------------------------
  [0 .. 4)                4           magic, 4 ASCII bytes, payload-kind
                                      specific (see section 2)
  [4 .. 8)                4           version : u32 LE, envelope+payload
                                      schema version, starts at 1. An
                                      INCREMENTAL INTEGER (1, 2, 3, ...),
                                      never semver: a reader compares, it
                                      does not parse. It declares the
                                      MINIMUM grammar revision needed to
                                      read this file COMPLETELY — see
                                      section 5a.
  [8 .. 12)               4           header_len : u32 LE, byte length of
                                      the MessagePack header
  [12 .. 12+header_len)   header_len  header : MessagePack map (section 3)
  [12+header_len .. P)    pad         zero bytes, count = P-(12+header_len)
  [P .. file_end)         *           payload sections (section 5)

  where P = payload_origin = 16 * ceil((12 + header_len) / 16)

  P is ALSO written into the header as the key "payload_origin". A reader
  MUST verify that the computed and declared values agree and MUST reject
  the file if they do not. (The computation is given so a writer can produce
  the value; the declared value is the authority a reader checks against.
  Two independent statements of the same fact is how a truncated or
  hand-edited file is caught.)

  Padding bytes MUST be 0x00. A reader MUST NOT rely on this (it verifies
  nothing) but a writer that emits nonzero padding is non-conformant.

  Minimum legal file size is 12 bytes (empty header is illegal: the header
  map has mandatory keys, so header_len >= 1 always).

--------------------------------------------------------------------------
2. Magic values
--------------------------------------------------------------------------

  All magics are exactly 4 bytes of ASCII, no NUL, no version digit — the
  version is the u32 at offset 4.

  ASCII      hex            payload kind        layout file
  ---------  -------------  ------------------  -------------------------
  "WKFF"     57 4B 46 46    flow field grid     flowfield.layout.txt
  "WKRP"     57 4B 52 50    settled rest poses  restposes.layout.txt
  "WKAC"     57 4B 41 43    animation clip      animclip.layout.txt
  "WKSK"     57 4B 53 4B    skeleton mirror     skeleton.layout.txt
  "WKEM"     57 4B 45 4D    style embedding +   embedding.layout.txt
                            palette
  "WKPC"     57 4B 50 43    point cloud         points.layout.txt
  "WKGS"     57 4B 47 53    3D Gaussian splat   gsplat.layout.txt
  "WKX0".."WKX9"            any binary this     supplied by whoever defines
                            file does not       the payload, who MUST ship
                            define: a profile's its *.layout.txt in the
                            own core.* binaries package and name it in the
                            and x.* binaries    manifest's `layouts` map

  RECOGNITION (ruling 4 of 2026-10-13, PROPOSED; SPEC.md section 3.1).
  A file is an envelope when its first four bytes are

      'W' 'K' c c        each c one of  A..Z  or  0..9

  and its node does not declare it to be in another format. Every magic in
  the table has that shape, and so will any magic a later revision reserves.
  A reader validates the FRAME of every such file - sections 1, 3, 5 and 7
  of this document - whatever its magic, and says how many it validated.

  The seven magics in the table are RESERVED and each binds one `kind`
  (section 3): "WKFF" core.field.flow, "WKRP" core.pose.rest, "WKAC"
  core.anim.clip, "WKSK" core.skeleton, "WKEM" core.embedding, "WKPC"
  core.geom.points, "WKGS" core.geom.gsplat. A reserved magic over a header
  that says another kind is malformed. THAT TABLE IS A CONSISTENCY CHECK AND
  NOT A RECOGNISER: until this revision a reader recognised an envelope only
  if its magic was in the reader's own copy of the table, there were four
  copies, and a magic missing from one of them was not parsed there and not
  reported. A reader that meets a "WK" magic it has no entry for has met an
  envelope, validates its frame, and finds its grammar exactly as below.

  "WKX0".."WKX9" bind NO kind. The digit means nothing and two different
  kinds may share one magic. What identifies an envelope's contents is the
  header's `kind`, and what describes them is the grammar the manifest's
  `layouts` map names for that kind:

      grammar of an envelope  =  MANIFEST.json -> layouts[ header.kind ]

  Outside a `core.spec` node, `kind` equals the `type` of the node the file
  belongs to. An envelope inside a `core.spec` node is a worked example; its
  kind is the type it illustrates.

  A frame that fails validation marks that node unreadable and the load
  continues (law 3). Unknown-because-newer and broken degrade identically,
  and neither is silent.

--------------------------------------------------------------------------
3. The header map
--------------------------------------------------------------------------

  The header is one MessagePack map with string keys. These keys are
  MANDATORY in every envelope, of every kind:

  key              type            meaning
  ---------------  --------------  -------------------------------------
  "kind"           str             node type id, e.g. "core.field.flow".
                                   MUST match the magic per section 2.
  "endianness"     str             MUST be exactly "le". Present so the
                                   file states its own byte order rather
                                   than relying on this document.
  "payload_origin" uint            P, absolute byte offset of section 0.
  "payload_size"   uint            total bytes from P to end of file.
                                   file_size == payload_origin+payload_size
                                   MUST hold.
  "sections"       array of map    one entry per payload section, in file
                                   order, no gaps permitted except
                                   alignment padding (section 5).

  Each element of "sections" is a map with these MANDATORY keys:

  key         type        meaning
  ----------  ----------  ----------------------------------------------
  "name"      str         kebab-case section id, unique within the file.
  "offset"    uint        ABSOLUTE byte offset from the start of the FILE
                          (not relative to payload_origin). Declared, not
                          derived.
  "size"      uint        exact byte length of the section.
  "dtype"     str         element type, from the table in section 6.
  "shape"     array<uint> logical dimensions, slowest-varying dimension
                          FIRST (C order). Example [128,64,64,3] is 128
                          planes of 64 rows of 64 elements of 3 scalars.
  "stride"    uint        bytes between the start of consecutive REPEATS of
                          whatever unit this section repeats: one scalar, or
                          one whole element (a component vector, a record).
                          Which of the two it is, is DERIVED from "stride"
                          itself by the rule below — never guessed, never
                          taken from a comment. Declaring the stride is what
                          makes reserved/padding bytes inside a record legal
                          and explicit.

  Consistency rule a reader MUST check. It is an algorithm, not a sentence,
  because the earlier prose version could not be executed:

      esz = byte size of "dtype" from section 6
            ("record" has no fixed size: define esz = stride)

      if stride == esz:
          # the stride spans ONE SCALAR, so every entry of "shape" is an
          # array dimension and none of them is a component count
          size == stride * product(shape[0..n-1])          # all entries

      else:                       # stride > esz necessarily
          # the stride spans the LAST dimension: shape[-1] is a component
          # count (or the record's field count is irrelevant and shape[-1]
          # is absent — see the one-dimensional record case below)
          stride >= esz * shape[-1]                        # MUST hold
          size   == stride * product(shape[0..n-2])        # all but last

  The `stride >= esz * shape[-1]` inequality (rather than equality) is what
  permits declared padding inside a record; the surplus bytes are described
  by the per-magic layout file's field table.

  Worked, against every section this spec actually defines, so the rule can
  be checked rather than believed:

    poses     dtype "record" shape [pose_count]      stride 32
              esz = 32 = stride  -> first branch  -> size = 32*pose_count
    contacts  dtype "f32"    shape [contact_count,3] stride 12
              esz = 4 != 12      -> second branch -> 12 >= 4*3, and
                                                     size = 12*contact_count
    sdf       dtype "f32"    shape [nz,ny,nx]       stride 4
              esz = 4 = stride   -> first branch  -> size = 4*nz*ny*nx
    flow      dtype "f32"    shape [nz,ny,nx,3]     stride 12
              esz = 4 != 12      -> second branch -> size = 12*nz*ny*nx
    root      dtype "f32"    shape [frame_count,7]  stride 28
              esz = 4 != 28      -> second branch -> size = 28*frame_count
    bones     dtype "f32"    shape [bone_count,frame_count,4] stride 16
              esz = 4 != 16      -> second branch ->
                                     size = 16*bone_count*frame_count
    skel-bin  dtype "record" shape [bone_count]     stride 48
              esz = 48 = stride  -> first branch  -> size = 48*bone_count
    json-blob dtype "u8"     shape [size]           stride 1
              esz = 1 = stride   -> first branch  -> size = 1*size
    vector    dtype "f32"    shape [dim]            stride 4
              esz = 4 = stride   -> first branch  -> size = 4*dim
    palette   dtype "f32"    shape [swatches,4]     stride 16
              esz = 4 != 16      -> second branch -> 16 >= 4*4, and
                                                     size = 16*swatches
    means     dtype "f32"    shape [count,3]        stride 12
              esz = 4 != 12      -> second branch -> size = 12*count
    rotations dtype "f32"    shape [count,4]        stride 16
              esz = 4 != 16      -> second branch -> size = 16*count
    opacities dtype "f32"    shape [count]          stride 4
              esz = 4 = stride   -> first branch  -> size = 4*count
    sh-rest   dtype "f32"    shape [count,K-1,3]    stride 12
              esz = 4 != 12      -> second branch -> size = 12*count*(K-1),
                                                     and 0 when K == 1
    pc-color  dtype "u8"     shape [count,C]        stride C
              esz = 1 != C       -> second branch -> C >= 1*C, and
                                                     size = C*count
              (C is the field's declared component count, 3 or 4: a WKPC
               colour field may or may not carry alpha, and the row is
               written with the symbol rather than a number so nobody reads
               an ILLUSTRATION as a statement about a particular file. A
               cold reader of the first WKPC package went looking for an
               alpha channel that was not there.)

  A zero-size section satisfies the rule trivially: some entry of "shape" is
  0, so the product is 0.

  The two branches agree whenever shape[-1] == 1, so no section is ambiguous
  and no reader has to choose. EVERY layout file in this spec ALSO states,
  per section, the exact arithmetic that must hold; when this document and a
  specific layout file disagree, the specific layout file wins for that
  magic. (Recorded as Stage 1 decision 19.)

  Optional common keys, permitted in any envelope:

  key            type    meaning
  -------------  ------  ------------------------------------------------
  "note"         str     free text. Never load-bearing.
  "input_hash"   str     lowercase hex sha256 over the node's declared
                         inputs (law 5). Mandatory for derived nodes; the
                         manifest also carries it, and the two MUST agree.
  "producer"     map     {"tool":str,"version":str,"model":str?}
  "epistemic"    str     "authored" | "measured" | "inferred"
  "confidence"   float   0.0 .. 1.0, only meaningful with "inferred"

  Per-kind keys are defined by the per-kind layout files. A reader MUST
  ignore header keys it does not know (law 12).

--------------------------------------------------------------------------
4. The MessagePack subset used by werk headers
--------------------------------------------------------------------------

  werk uses a deliberately small subset so this section can be a complete
  specification. A reader written from this table alone will read every
  conformant werk header.

  IMPORTANT: all multi-byte integers and floats INSIDE MessagePack are
  BIG-ENDIAN (network order). This is the opposite of the payload. Get this
  wrong and header_len will look sane while every number is garbage.

  4.1 Format bytes

  first byte(s)   type        payload that follows
  --------------  ----------  ------------------------------------------
  0x00..0x7f      uint        none; value = the byte itself (0..127)
  0xe0..0xff      int         none; value = byte - 256 (-32..-1)
  0xc0            nil         none
  0xc2            false       none
  0xc3            true        none
  0xcc            uint8       1 byte
  0xcd            uint16      2 bytes BE
  0xce            uint32      4 bytes BE
  0xcf            uint64      8 bytes BE
  0xd0            int8        1 byte, two's complement
  0xd1            int16       2 bytes BE, two's complement
  0xd2            int32       4 bytes BE, two's complement
  0xd3            int64       8 bytes BE, two's complement
  0xca            float32     4 bytes BE, IEEE-754 binary32
  0xcb            float64     8 bytes BE, IEEE-754 binary64
  0xa0..0xbf      str         len = (byte & 0x1f), then len UTF-8 bytes
  0xd9            str8        1 byte len, then len UTF-8 bytes
  0xda            str16       2 bytes BE len, then len UTF-8 bytes
  0xdb            str32       4 bytes BE len, then len UTF-8 bytes
  0xc4            bin8        1 byte len, then len raw bytes
  0xc5            bin16       2 bytes BE len, then len raw bytes
  0xc6            bin32       4 bytes BE len, then len raw bytes
  0x90..0x9f      array       n = (byte & 0x0f), then n encoded values
  0xdc            array16     2 bytes BE n, then n encoded values
  0xdd            array32     4 bytes BE n, then n encoded values
  0x80..0x8f      map         n = (byte & 0x0f), then n (key,value) pairs
  0xde            map16       2 bytes BE n, then n (key,value) pairs
  0xdf            map32       4 bytes BE n, then n (key,value) pairs

  4.2 Banned in werk headers — a reader MUST reject the header (and mark
  the node dead) if it encounters any of:

  0xc1            never-used byte
  0xc7 0xc8 0xc9  ext8 / ext16 / ext32
  0xd4..0xd8      fixext1 / fixext2 / fixext4 / fixext8 / fixext16

  Extension types are banned because they smuggle application knowledge
  into the payload, which law 1 forbids.

  4.3 Canonical encoding (writers MUST, readers MUST NOT depend on it)

  So that identical headers hash identically (the manifest's sha256 is the
  store key — see the manifesto's Companion section), a writer MUST:
    * use the SHORTEST encoding that represents each integer exactly;
    * encode every non-integral number as float64 (0xcb), never float32;
    * encode every string as the shortest str form;
    * emit map keys sorted ascending by their raw UTF-8 byte sequence;
    * never emit nil for an absent optional key — omit the key instead.
  A reader MUST accept any legal encoding from the table in 4.1, because a
  non-canonical header is still a readable header.

  4.4 Worked example

  Header {"endianness":"le","kind":"core.pose.rest"} encodes as:

    82                                map, 2 pairs
    aa 65 6e 64 69 61 6e 6e 65 73 73  fixstr(10) "endianness"
    a2 6c 65                          fixstr(2)  "le"
    a4 6b 69 6e 64                    fixstr(4)  "kind"
    ae 63 6f 72 65 2e 70 6f 73 65 2e  fixstr(14) "core.pose.rest"
    72 65 73 74
                                      = 35 bytes, so header_len = 35,
                                      12+35 = 47, P = 48, pad = 1 byte.
  (Keys are sorted: "endianness" < "kind" bytewise. The real header for
  that kind has more mandatory keys; this shows only the encoding.)

  Count it yourself, because an illustration that disagrees with section 4.1
  is worse than no illustration: 1 (map header) + 1+10 ("endianness")
  + 1+2 ("le") + 1+4 ("kind") + 1+14 ("core.pose.rest") = 35. The fixstr
  lead byte is 0xa0 | len, so a 14-byte string is 0xae, not 0xaf.
  (Earlier revisions of this file printed af / 34 / pad 2. payload_origin
  came out as 48 either way, which is exactly why the error survived a
  read-through. Recorded as Stage 1 decision 18.)

--------------------------------------------------------------------------
5. Payload sections
--------------------------------------------------------------------------

  * Section 0 starts exactly at payload_origin.
  * Every section's "offset" MUST be a multiple of 16.
  * Sections appear in the file in the same order as in "sections".
  * Between the end of one section and the offset of the next there may be
    0..15 zero padding bytes and nothing else.
  * The last section's offset+size, rounded UP to a multiple of 16, MUST
    equal payload_origin+payload_size. Trailing padding to the 16-byte
    boundary is legal; trailing data is not.
  * A section of size 0 is legal (an empty array). Its offset must still be
    aligned and declared.

--------------------------------------------------------------------------
5a. Unknown sections, and what the version integer promises
--------------------------------------------------------------------------

  Sections are found BY NAME, never by position. "sections" is a declared
  table of {name, dtype, shape, stride, offset, size}, and a reader looks up
  the name it wants. This is the whole reason offsets are declared rather
  than derived from a struct, and it is what makes the format additive
  (law 12) instead of versioned-and-brittle.

  Therefore, NORMATIVELY:

  * A reader that meets a section whose "name" it does not recognise MUST
    SKIP IT AND REPORT IT (report code "section-skipped-unknown", severity
    info). It MUST NOT guess at its meaning, MUST NOT treat it as damage,
    and MUST NOT fail the node. Unknown-because-newer and unknown-because-
    third-party degrade through the same path, which is the same rule
    section 2 already states for magics.
  * A reader MUST still apply section 5's consistency rules to an unknown
    section: its offset is aligned, it is in file order, and it is inside
    payload_size. An unknown section is skipped, not unchecked.
  * THE VERSION INTEGER DECLARES THE MINIMUM GRAMMAR REVISION NEEDED TO
    READ THE FILE COMPLETELY. A writer emits the LOWEST revision whose
    grammar covers everything the file actually uses — so a payload that
    uses no feature added after revision 1 is still written as version 1,
    byte-for-byte as before, and every existing reader keeps working.
  * A reader that finds a version HIGHER than the revision it implements
    MUST NOT refuse the file on the version alone. It reports
    "layout-version-newer" (info), reads every section it recognises, skips
    the rest by the rule above, and states in its report that it read the
    file partially. Refusing a payload it can substantially read is exactly
    law 3's failure mode: ninety live nodes thrown away because one thing
    was newer than the reader.
  * A reader that DOES implement the revision a section belongs to MUST use
    that section. Silently dropping declared data it knows how to read is a
    bug, not degradation, and it is invisible without this sentence.

  The one thing a higher version legitimately warns about is a change to a
  section a reader ALREADY knows. No such change has ever been made; if one
  ever is, it gets a new section NAME rather than new semantics under an old
  one, precisely so that the rules above stay sufficient.

6. dtype vocabulary
--------------------------------------------------------------------------

  dtype string   bytes   meaning
  -------------  ------  ----------------------------------------------
  "u8"           1       unsigned 8-bit
  "i8"           1       signed 8-bit, two's complement
  "u16"          2       unsigned 16-bit LE
  "i16"          2       signed 16-bit LE, two's complement
  "u32"          4       unsigned 32-bit LE
  "i32"          4       signed 32-bit LE, two's complement
  "u64"          8       unsigned 64-bit LE
  "i64"          8       signed 64-bit LE, two's complement
  "f32"          4       IEEE-754 binary32, LE
  "f64"          8       IEEE-754 binary64, LE
  "record"       n/a     a heterogeneous fixed-stride record; the layout
                         file for that magic gives the byte-exact field
                         table, and "stride" gives the record size

  numpy equivalents, for the avoidance of doubt:
    u8=uint8 i8=int8 u16=<u2 i16=<i2 u32=<u4 i32=<i4 u64=<u8 i64=<i8
    f32=<f4 f64=<f8

  Float rules: no NaN and no infinity may appear in any core payload. A
  reader encountering either MUST mark the node dead and report it. (An
  extension namespace may do as it likes.)

  Quaternion rule: wherever a quaternion appears in any core payload its
  component order is w,x,y,z — declared in the manifest as
  conventions.quat_order = "wxyz". Quaternions are unit length; a reader
  MUST accept |q| within 1e-6 of 1.0 and MAY renormalise. w >= 0 is the
  canonical sign; writers MUST emit the w >= 0 representative.

--------------------------------------------------------------------------
7. Reference reader (normative pseudocode)
--------------------------------------------------------------------------

  read_envelope(path):
      buf         = read whole file
      magic       = buf[0:4]                       # 4 ASCII bytes
      version     = u32_le(buf, 4)
      header_len  = u32_le(buf, 8)
      assert 12 + header_len <= len(buf)
      header      = msgpack_decode(buf[12 : 12+header_len])   # section 4
      assert header["endianness"] == "le"
      P           = 16 * ceil((12 + header_len) / 16)
      assert header["payload_origin"] == P
      assert P + header["payload_size"] == len(buf)
      for s in header["sections"]:
          assert s["offset"] % 16 == 0
          assert s["offset"] + s["size"] <= len(buf)
          esz = dtype_size(s["dtype"]) or s["stride"]   # "record" -> stride
          if s["stride"] == esz:
              assert s["size"] == s["stride"] * prod(s["shape"])
          else:
              assert s["stride"] >= esz * s["shape"][-1]
              assert s["size"] == s["stride"] * prod(s["shape"][:-1])
          data = buf[s["offset"] : s["offset"] + s["size"]]
          # interpret with s["dtype"], s["shape"], s["stride"]
      return magic, version, header, sections

  Any failed assertion => node is dead. Log which assertion, skip the node,
  load the rest of the package. Never guess.

--------------------------------------------------------------------------
8. Decisions recorded here (Stage 1)
--------------------------------------------------------------------------

  D-ENV-1  The per-kind "header" is the MessagePack map, not a fixed binary
           struct. Earlier drafts of the profile sketched fixed structs
           (e.g. "dims u32x3, cell_size f32, origin f32x3"). Those fields
           still exist, byte-for-byte identical in meaning, but they live as
           named header keys. Reason: law 8's corollary demands that every
           offset and size be declared rather than derived from a struct
           definition, and a fixed struct forces derivation the moment a
           field is added. The per-kind layout files list the exact keys.

  D-ENV-2  MessagePack, not JSON, for the header — as briefed — even though
           it costs this document section 4. The offsetting benefit is that
           header parsing needs no float text round-tripping, so byte
           identity on rewrite (Stage 2's gate) is trivially achievable.
           Section 4 exists so law 2's "no external knowledge" guarantee
           holds literally.

  D-ENV-3  Section offsets are absolute file offsets, not relative to
           payload_origin. Absolute offsets survive being copied into a
           mmap slice table and cannot be misinterpreted by one frame of
           reference.
