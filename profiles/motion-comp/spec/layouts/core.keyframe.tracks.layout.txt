werk keyframe tracks - layout grammar v1  (magic "WKX3")
=======================================================

Applies to: `core.keyframe.tracks` (profile `motion-comp/1`) - the numeric
keyframes of the properties of ONE owner: a layer, or a composition's own
properties. Which owner is said twice: by the node's `requires` edge (role
`animates`) and by the header key "owner".

Read `spec/layouts/ENVELOPE.layout.txt` FIRST. It defines the 4-byte magic,
the u32 version, the u32 header length, the MessagePack header subset, the
16-byte payload alignment and the section consistency rule. Everything below
is the WKX3-specific part.

What the numbers MEAN - how a value is interpolated between two keys - is
`spec/PROFILE-MOTION-COMP.md` sections 6.3 and 6.4. This file says only where
the numbers are.

--------------------------------------------------------------------------
0. Why a binary at all
--------------------------------------------------------------------------

A keyframe is 13 fields. A layer with a few thousand keys (a tracked point, a
baked simulation) is megabytes of JSON, and every Save of that layer would
store them again. As flat arrays they are 70 bytes per scalar key before the
eases, they are exact to the bit, and the layer's JSON - what a person edits
- stays small and separate from them. A property whose keys are not all finite
numbers of one kind keeps them in the owner's JSON (`keys`), where anything
can be said.

--------------------------------------------------------------------------
1. Fixed prefix
--------------------------------------------------------------------------

  [0 .. 4)    magic  = "WKX3"  = 57 4B 58 33
  [4 .. 8)    version : u32 LE = 1
  [8 .. 12)   header_len : u32 LE
  [12 .. 12+header_len)  MessagePack header (section 2)
  padding of zero bytes to the next 16-byte boundary
  payload sections (section 3), each starting on a 16-byte boundary

--------------------------------------------------------------------------
2. Header keys
--------------------------------------------------------------------------

  Mandatory envelope keys, per ENVELOPE.layout.txt section 3:
    "kind"            = "core.keyframe.tracks"
    "endianness"      = "le"
    "payload_origin"  uint
    "payload_size"    uint
    "sections"        array of section maps

  Mandatory WKX3 keys:

  key                 type          meaning
  ------------------  ------------  ------------------------------------------
  "owner"             str           node id of the owner (`layer-12`, `comp-3`).
  "ticks_per_second"  uint          254016000000. The unit of section "at".
  "interpolations"    array of str  ["Linear", "Bezier", "Hold"]: the words the
                                    codes 0, 1, 2 of section "interp" stand for.
  "tracks"            array of map  one entry per track, in INDEX ORDER: entry i
                                    is the track a property names with
                                    `"track": i`.

  Each element of "tracks":

  key            type  meaning
  -------------  ----  ---------------------------------------------------
  "uid"          uint  uid of the property the track belongs to. A cross-
                       check: the binding is the index. A property that
                       names track i while entry i has another uid has lost
                       its keys: it keeps its static value and the reader
                       says so.
  "kind"         str   "scalar", "vec2", "vec3" or "color": the kind of every
                       key value (Scalar, Vec2, Vec3, Color).
  "components"   uint  numbers per value: 1, 2, 3, 4 for the four kinds.
  "keys"         uint  number of keys of the track, >= 1.
  "first_key"    uint  index of the track's first key in the per-key sections.
  "first_value"  uint  index of the first number of its first key in "value".
  "first_ease"   uint  index of the first ease record of its first key in
                       "ease".

  Tracks are stored one after another without gaps: track i+1 has
  first_key = first_key(i) + keys(i), first_value = first_value(i) +
  keys(i) * components(i), and its first_ease follows the last ease of
  track i. A reader MUST ignore header keys it does not know.

--------------------------------------------------------------------------
3. Payload sections
--------------------------------------------------------------------------

  K = total number of keys of all tracks, V = total number of value numbers,
  E = total number of ease records. Eight sections, in this order; a reader
  finds them BY NAME.

  name          dtype  shape   stride  arithmetic that MUST hold
  ------------  -----  ------  ------  ---------------------------------
  "at"          i64    [K]     8       size == 8 * K
  "interp"      u8     [K,2]   2       size == 2 * K
  "flags"       u8     [K]     1       size == K
  "label"       u8     [K]     1       size == K
  "value"       f64    [V]     8       size == 8 * V
  "spatial"     f64    [K,6]   48      size == 48 * K
  "ease-count"  u8     [K,2]   2       size == 2 * K
  "ease"        f64    [E,2]   16      size == 16 * E

  All numbers little-endian. f64 is IEEE-754 binary64; no NaN and no
  infinity.

  "at"          key k: its time, in ticks, in the owner's time (a layer's
                keys: layer time; a composition's: composition time). Within
                a track strictly ascending.
  "interp"      key k: two codes, (in_interp, out_interp), each 0 Linear,
                1 Bezier, 2 Hold. Any other code: the file is refused.
  "flags"       key k: bit 0 `continuous`, bit 1 `auto_bezier`,
                bit 2 `spatial_auto`, bit 3 `spatial_continuous`,
                bit 4 `roving`. Bits 5..7 are 0.
  "label"       key k: the key's colour label, 0..16.
  "value"       the numbers of the values, key after key: key j of a track
                (j from 0) has its `components` numbers at
                first_value + j * components.
  "spatial"     key k: six numbers: spatial_in (x, y, z), spatial_out (x, y, z).
                Stored for every key; meaningful only for a spatial property
                whose key has `spatial_auto` false.
  "ease-count"  key k: two counts, (number of in eases, number of out eases),
                each 0..255.
  "ease"        ease records (speed, influence), 16 bytes each. The records
                of one key are consecutive: first its in eases, then its out
                eases. The records of key j of a track start where those of
                key j-1 end; those of key 0 at the track's first_ease.

--------------------------------------------------------------------------
4. Reading track i back into keyframes
--------------------------------------------------------------------------

    t = header["tracks"][i];  c = t["components"];  e = t["first_ease"]
    for j in 0 .. t["keys"] - 1:
        k = t["first_key"] + j
        key.time        = at[k]
        key.value       = value[t["first_value"] + j*c .. + c]   as t["kind"]
        key.in_interp   = interpolations[interp[2k]]
        key.out_interp  = interpolations[interp[2k + 1]]
        key.continuous, auto_bezier, spatial_auto, spatial_continuous, roving
                        = bits 0..4 of flags[k]
        key.label       = label[k]
        key.spatial_in  = spatial[6k .. 6k+3];  key.spatial_out = spatial[6k+3 .. 6k+6]
        n_in, n_out     = ease-count[2k], ease-count[2k + 1]
        key.in_ease     = n_in  records (speed, influence) from ease[e ..];  e += n_in
        key.out_ease    = n_out records from ease[e ..];                     e += n_out

  The result is exactly the list of keyframe objects the owner's JSON would
  hold as `keys` (schema `$defs/keyframe`): the two spellings carry the same
  fields. Every index MUST lie inside its section; a file in which one does
  not is refused whole (the node is dead, the owner's properties keep their
  static values).

--------------------------------------------------------------------------
5. Writing
--------------------------------------------------------------------------

  Lay the tracks out in index order, fill the eight sections, build the
  header with the canonical MessagePack encoding of ENVELOPE.layout.txt
  section 4.3 (map keys sorted by their bytes, shortest integer forms), pad
  to 16 bytes, and place each section on the next 16-byte boundary after the
  one before, zero bytes between. "payload_origin" is the offset of section
  "at"; "payload_size" runs from there to the end of the file, which is the
  16-byte boundary after the last section (zero bytes fill it). A zero-size
  section has the offset where it would start.
