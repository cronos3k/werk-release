x.cub.v1 baked geometry — layout grammar v1
===========================================

Applies to: the payload of a `x.cub.v1.geom.baked` node — the CUB engine's
cooked vertex tier. Magic "WKX0".

This file is normative for this payload kind and self-contained in the sense
spec/layouts/ENVELOPE.layout.txt is: read that file first for the envelope
frame (magic / version / header_len / MessagePack header / 16-byte-aligned
payload sections), then this file for what the sections contain.

It travels inside every werk package that carries an `x.cub.v1.*` node,
because SPEC.md section 8 requires an extension binary to ship its own
*.layout.txt, and law 1 does not make an exception for extensions.

--------------------------------------------------------------------------
0. What this node is, and what it is not
--------------------------------------------------------------------------

  It is the same triangles as `core.geom.game`, already interleaved in the
  exact 144-byte struct the CUB renderer binds as a vertex buffer, plus the
  baked per-vertex lighting a GLB has no way to carry.

  It is NOT the truth about shape. `core.geom.game` is. The edge from this
  node to the game mesh is `enhances`, never `requires`: a reader that skips
  this node parses the GLB and gets the same geometry with default lighting.
  That is the whole degradation ladder for this feature, and it is one rung.

  A consumer that is not CUB should skip this node. It will lose nothing it
  can use: the field semantics below are specific to one renderer's shading
  model, and pretending otherwise would be dishonest.

--------------------------------------------------------------------------
1. Magic and version
--------------------------------------------------------------------------

  ASCII      hex            meaning
  ---------  -------------  --------------------------------------------
  "WKX0"     57 4B 58 30    extension binary, slot 0

  ENVELOPE.layout.txt section 2 reserves "WKX0".."WKX9" for extension
  binaries and forbids a bespoke magic, so the four bytes do not identify
  this payload on their own. The header's mandatory "kind" key does:

      kind == "x.cub.v1.geom.baked"

  A reader MUST check "kind" and MUST NOT dispatch on the magic alone.

  The u32 at offset 4 is the envelope+payload schema version and is 1.
  A reader that supports version 1 and meets a higher number marks the node
  unreadable and continues (law 3) — it does not attempt a partial read.

--------------------------------------------------------------------------
2. Header keys, beyond the envelope's mandatory set
--------------------------------------------------------------------------

  key                   type     meaning
  --------------------  -------  ------------------------------------------
  "kind"                str      "x.cub.v1.geom.baked" (mandatory, above)
  "engine"              str      "cub"
  "vertex_format"       str      "BakedVertex"
  "vertex_stride"       uint     144. A reader MUST compare this with its own
                                 struct size and MUST refuse the node if they
                                 differ, rather than reinterpreting bytes.
  "vertex_count"        uint     number of vertices
  "index_count"         uint     number of indices (a multiple of 3)
  "index_dtype"         str      "u32". Always. CUB does not emit u16 indices
                                 in this tier — a mesh small enough for u16 is
                                 not the mesh whose load time anyone measures,
                                 and one width means one code path.
  "primitive_topology"  str      "triangle-list"
  "sh_l1_order"         array    ["dc","y","z","x"] — MUST equal the
                                 manifest's conventions.sh_l1_order.
  "oct_encoding_pole"   str      "y" — MUST equal conventions.oct_encoding_pole.
  "layout_file"         str      path of this file inside the package.
  "fields"              array    the field table of section 4, as data. See
                                 section 4 for why it is duplicated there.
  "input_hash"          str      sha256 over the inputs this was cooked from
                                 (law 5), matching the manifest node version's
                                 input_hash. Present whenever the node is
                                 `measured`, which it always is.
  "producer"            map      {"tool","version"}
  "epistemic"           str      "measured"

--------------------------------------------------------------------------
3. Payload sections
--------------------------------------------------------------------------

  section 0   name "vertices"
              dtype  "record"
              shape  [vertex_count]
              stride 144
              size   144 * vertex_count
              (esz = stride for "record", so the ENVELOPE section 3
               consistency rule takes its FIRST branch)

  section 1   name "indices"
              dtype  "u32"
              shape  [index_count]
              stride 4
              size   4 * index_count
              (esz = 4 = stride, FIRST branch again)

  Both offsets are absolute file offsets and multiples of 16, declared in the
  header. A reader slices at those offsets and memcpys. That is the entire
  load: no attribute walk, no accessor arithmetic, no index widening.

  Index values are vertex indices into section 0, already rebased across every
  source primitive so the whole mesh is one draw call.

--------------------------------------------------------------------------
4. The BakedVertex record — 144 bytes, little-endian, every field f32
--------------------------------------------------------------------------

  offset  count  field              meaning
  ------  -----  -----------------  -------------------------------------
       0      3  position           metres, werk model space (+Y up, -Z
                                    forward, +X right)
      12      3  normal             unit length, same space
      24      2  uv                 TEXCOORD_0, origin top-left
      32      4  tangent            xyz unit tangent, w bitangent sign
                                    (+1 or -1 exactly), MikkTSpace
      48      1  material_id        index into the manifest's materials[],
                                    stored as f32 because the vertex format
                                    is homogeneous f32 and a u32 bitcast in
                                    a vertex attribute is a portability trap
      52      4  sh_r               SH-L1 irradiance, red
      68      4  sh_g               SH-L1 irradiance, green
      84      4  sh_b               SH-L1 irradiance, blue
     100      1  curvature          signed, from the surface bake
     104      1  cavity             0..1, 1 = fully open
     108      2  bent_normal_oct    octahedral, pole +Y (see header key)
     116      4  tex_slots_0        albedo, normal, roughness, metallic
     132      2  tex_slots_1        ao, emissive
     140      1  _pad               reserved, MUST be written as 0.0

  Component order inside each SH quadruple is the manifest's
  conventions.sh_l1_order, which is ["dc","y","z","x"] — DC term first, then
  the three linear terms in Y, Z, X order. This is NOT the order most
  references print (they usually use x,y,z), and it is declared numerically
  for exactly that reason.

  The same table is repeated in the header's "fields" key. That duplication is
  deliberate and it is law 8's corollary: the file states its own offsets as
  data, so a reader validates them instead of trusting this document. If the
  two ever disagree, the header is what the bytes actually are and this file
  is what someone meant — treat the disagreement as damage and mark the node
  dead.

  Float rule inherited from ENVELOPE section 6: no NaN and no infinity.

--------------------------------------------------------------------------
5. Recomputing this node from the core tier
--------------------------------------------------------------------------

  A consumer that distrusts the cooked tier (law 5: validate-or-recompute,
  never trust) rebuilds it from `core.geom.game`:

    position, normal, uv, tangent, material_id   <- the GLB attributes
    sh_r, sh_g, sh_b                             <- 0.5 in the DC term, 0
                                                    elsewhere, if no bake
    curvature                                    <- 0.0
    cavity                                       <- 1.0
    bent_normal_oct                              <- oct_encode(normal)
    tex_slots_0, tex_slots_1                     <- 0.0
    _pad                                         <- 0.0

  Those defaults are what a GLB-only reader produces, and they are the honest
  floor: the cooked node exists because a real bake has better numbers for the
  lighting fields, not because the geometry differs.

  "input_hash" is the sha256 defined in MINI-SPECS section 11: the 32 raw
  digest bytes of each file named by the node version's input_files, in that
  order, followed by the UTF-8 bytes of the canonical JSON of input_params —
  which is the two bytes {} when there are none. If the recomputed hash does
  not match, the cooked tier is stale and the reader falls back to the GLB.
